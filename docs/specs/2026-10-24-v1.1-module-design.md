# Дизайн релиза 1.1: ядро как модуль, описание алгоритма, шесть исправлений

Дата: 2026-10-24. Продолжение [design.md](design.md) (версия 1.0.0).

## 1. Замысел

Версия 1.0 решает задачу как страница для нетехнического пользователя. Но настоящая цель репозитория другая: показать, как аккуратно решается типичная бизнес-задача «привести адреса к единому виду и получить координаты», и отдать механизм тем, кому он нужен в собственной системе. Страница при этом остаётся живой демонстрацией, а не продуктом для массового пользователя.

Разработчик, пришедший в репозиторий, забирает механизм одним из двух способов:

1. Подключает готовый JS-модуль: `npm install` или копирование одного файла.
2. Читает описание алгоритма на языке, не привязанном к JS, переписывает на своём языке (Python, 1С, Go, что угодно) и проверяет себя на тех же тестовых векторах.

Сейчас оба пути закрыты: ядро живёт внутри `index.html` блоком `<script id="core">`, а алгоритм описан только в коде и обрывочно в README.

## 2. Цели, не-цели, анти-цели

Цели:
- Ядро `AddrCore` живёт в отдельном файле, подключаемом и из браузера, и из Node, и опубликовано в npm.
- Описание алгоритма, достаточное для переписывания на другом языке без чтения JS.
- Тестовые векторы в формате, пригодном для любой реализации.
- Граница «геокодер / алгоритм» явная: ответ Яндекса превращается в нейтральный формат кандидата отдельной функцией-адаптером, и это задокументировано.
- Шесть отложенных исправлений из ревью 1.0 (раздел 5).
- Демо по-прежнему открывается двойным кликом с диска и работает на GitHub Pages.

Не-цели:
- Второй геокодер (DaData, 2ГИС, OSM). Только задокументированная точка расширения.
- Мобильная вёрстка.
- ФИАС/ГАР, индексы, квартиры.
- Сборщик, транспиляция, TypeScript. Файл ядра пишется руками и подключается как есть.

Анти-цели:
- Любой секрет в репозитории или в npm-пакете.
- Регресс честности: ни одно исправление не должно превратить «Город не подтверждён» в ложный «Подтверждён». Если сомнение, оставлять сомнительный статус.
- Страница перестала открываться с диска (ES-модули под `file://` блокируются Chrome, поэтому ядро не может быть `type="module"`).

## 3. Ограничения

- Без сборки и фреймворков, как в 1.0. SheetJS в `vendor/`, CSP, системные шрифты сохраняются.
- Node 22, `node:test`, без зависимостей в `package.json` (devDependencies допустимы только для проверок, не для сборки).
- npm-пакет публикуется с аккаунта автора; имя `address-standardization-russia` свободно (проверено 2026-10-24). Вход в npm на машине автора выполнен, двухфакторная защита включена на вход и на публикацию, поэтому `npm publish --access public` запускает автор сам и вводит одноразовый код; исполнитель готовит пакет и проверяет его `npm pack --dry-run`.
- Версия пакета и страницы одна: 1.1.0. Семантика: новый публичный API без изменения поведения существующих функций (кроме исправлений из раздела 5, которые только добавляют статусы «Подтверждён» там, где раньше было сомнение, или наоборот делают сомнение честнее).
- Любые адреса в тестах и примерах остаются адресами публичных зданий.
- Скрипт `check-clean` продолжает запрещать слова бренда и отрасли в любом файле репозитория, включая этот документ.

## 4. Решения

### 4.1. Файл ядра

Файл `addr-core.js` в корне репозитория. Формат: обычный скрипт с UMD-подобным хвостом.

```js
(function (root, factory) {
    if (typeof module === 'object' && module.exports) module.exports = factory();
    else root.AddrCore = factory();
}(typeof self !== 'undefined' ? self : this, function () {
    const AddrCore = {};
    // ... как сейчас ...
    return AddrCore;
}));
```

Почему так, а не ES-модуль: ES-модуль под `file://` не загружается в Chrome, а требование «открыть двойным кликом» остаётся. CommonJS-экспорт даёт `require('address-standardization-russia')` в Node и `import AddrCore from 'address-standardization-russia'` через совместимость Node ESM с CJS. Вариант «два файла, ESM и UMD» отвергнут: без сборки это дублирование вручную.

`index.html` подключает `<script src="addr-core.js"></script>` перед блоком `app`. Блок `<script id="core">` из HTML исчезает. `tests/load-core.mjs` вместо вырезания блока из HTML делает `createRequire(import.meta.url)('../addr-core.js')`; тест `load-core.test.mjs` переписывается под это.

Содержимое ядра не меняется по смыслу: те же функции, те же имена. Добавляется только то, что требуют исправления из раздела 5, и `AddrCore.VERSION = '1.1.0'`.

### 4.2. npm-пакет

> Итог релиза 1.1: публикация в реестр npm не выполнена, пакет устанавливается с GitHub по тегу (`npm install github:mad8fat/address-standardization-russia#v1.1.0`) и отдаётся через jsDelivr. Остальное в разделе описывает подготовку пакета, которая сделана.

`package.json`: убрать `"private": true` и `"type": "module"` (иначе `.js` считается ES-модулем и CommonJS-хвост `addr-core.js` не загрузится через `require`; все тесты и скрипты уже `.mjs`, им поле не нужно). Далее: `name` = `address-standardization-russia`, `version` = `1.1.0`, `main` = `addr-core.js`, `files` = `["addr-core.js", "README.md", "LICENSE", "docs/algorithm.md"]`, `license` = `MIT`, `repository`, `keywords` (геокодер, адрес, Яндекс, нормализация, Россия, geocoder, address, normalization, russia), `engines.node >= 18`. Страница, vendor, тесты и скриншоты в пакет не входят.

Публикация: `npm publish --access public` вручную автором после `npm login`. Автоматическая публикация из GitHub Actions не делается (потребовала бы токена в секретах репозитория, а анти-цель требует минимум секретов).

В README появляется раздел «Как встроить в своё приложение» с тремя путями: npm, копирование файла, переписывание по `docs/algorithm.md`. Пример в Node:

```js
const AddrCore = require('address-standardization-russia');
const url = AddrCore.buildGeocodeUrl(apiKey, AddrCore.cleanAddressForQuery(raw));
const json = await (await fetch(url)).json();
const cands = AddrCore.parseGeocoderResponse(json);
const cls = AddrCore.classify(raw, cands);
const rec = AddrCore.buildRecord({ original: raw, label: '', cands, cls });
```

### 4.3. Описание алгоритма

Файл `docs/algorithm.md`. Язык нейтральный: ни одной строки JS, только текст, таблицы и псевдокод там, где текст неоднозначен. Структура:

1. Задача и принцип: геокодер сопоставляет, а не проверяет; что именно проверяет алгоритм.
2. Формат кандидата (`Candidate`): поля `kind`, `precision`, `text`, `province[]`, `area`, `locality`, `street`, `house`, `lat`, `lon`, с правилом «последний `locality` из компонентов самый конкретный» и правилом «дом это `kind=house` или `kind=other` с номером дома».
3. Адаптер Яндекса: какой запрос (`results=10`, `bbox` России, `rspn=1`, `lang=ru_RU`), какие поля ответа куда ложатся. Пометка: это единственное место, зависящее от Яндекса; для другого геокодера пишется другой адаптер с тем же выходом.
4. Токенизация: нижний регистр, ё→е, разбиение по не-буквам и не-цифрам, отбрасывание слов короче трёх символов и стоп-слов (полный список стоп-слов приводится).
5. Очистка строки перед запросом: маркеры помещений, обрезание сегмента, выбрасывание чисто номерных сегментов после маркера, сохранение словесных сегментов. Правило «кв. как квартал» из раздела 5.3.
6. Раскрытие сокращений городов из раздела 5.1, со словарём.
7. Привязка: пул слов строки минус слова улицы кандидата; уровни `locality → area → province`; точное совпадение всех слов названия; предпочтение более длинного названия из раздела 5.2.
8. Подсчёт разных населённых пунктов среди кандидатов-домов и правило одноимённых городов в разных регионах.
9. Таблица статусов: условия в порядке проверки, с примерами на каждую строку.
10. Сборка записи: что попадает в результат при каждом статусе, особенно «Город не указан» без города и координат.
11. Тестовые векторы: ссылка на `tests/vectors/` и формат.

Каждый раздел сопровождается одним-двумя разобранными примерами из фикстур, чтобы читатель мог сверить своё понимание.

### 4.4. Тестовые векторы

Каталог `tests/vectors/` с JSON-файлами, по одному на группу:

```json
{
  "description": "Полные публичные адреса: все подтверждаются",
  "cases": [
    { "input": "г. Москва, ул. Тверская, 13", "candidates": [ ...Candidate... ],
      "expected": { "status": "Подтверждён", "anchor": "locality" } }
  ]
}
```

Поле `candidates` уже в нейтральном формате (после адаптера), чтобы вектор не зависел от Яндекса. Отдельный файл `tokenize.json` и `clean.json` с парами «вход → выход» для токенизации и очистки. Существующие `tests/fixtures/full.json` и `incomplete.json` уже хранят плоские кандидаты, а не сырые ответы: они конвертируются в векторы. Сырыми фикстурами адаптера остаются `raw-response.json` и `empty-response.json`. Тесты `core-*.test.mjs` переводятся на чтение векторов там, где это проверяет то же самое.

## 5. Шесть исправлений

Общее правило: каждое исправление начинается с теста, который падает на 1.0, и ни одно не имеет права дать «Подтверждён» там, где город в строке реально отсутствует.

### 5.1. Сокращения городов

Словарь `AddrCore.CITY_ABBREVIATIONS`, применяемый к исходной строке перед токенизацией (и в привязке, и в запросе к геокодеру). Начальный состав:

| Сокращение (регистр не важен, точки и пробелы допускаются) | Раскрытие |
|---|---|
| СПб, С.-Петербург, С-Петербург, Санкт Петербург | Санкт-Петербург |
| Н. Новгород, Н.Новгород, Нижний Новгород (без дефиса уже совпадает) | Нижний Новгород |
| Ростов н/Д, Ростов-на-Дону, Ростов на Дону | Ростов-на-Дону |
| Екб, Е-бург | Екатеринбург |
| Мск | Москва |
| Нск, Н-ск | Новосибирск |
| Влг | не раскрывается: Волгоград и Вологда неразличимы, оставить сомнение |

Раскрытие только по границам слов, чтобы «Мск» не нашёлся внутри «Омска». Словарь выносится в документацию и расширяется по запросам. Проверка: «СПб, Невский пр., 28» получает «Подтверждён» с привязкой `locality`.

### 5.2. Предпочтение более длинного названия

Текущая привязка: все слова названия кандидата встречаются в строке. «Ростов-на-Дону» токенизируется в «ростов», «дону», и кандидат «Ростов» (Ярославская область) проходит проверку по слову «ростов». Та же дыра у «Комсомольск-на-Амуре» / «Комсомольск» и у любого составного названия через дефис.

Исправление из двух правил, оба обязательны:

1. **Составное имя во входе не разбирается на части.** Слова входной строки, сцепленные дефисами (после раскрытия сокращений из 5.1), образуют составное имя. Вхождение слова названия кандидата внутри такого составного имени засчитывается только если название кандидата покрывает составное имя целиком (все его значимые слова). Слово засчитывается, если у него есть хотя бы одно допустимое вхождение: отдельно стоящее слово вне составных имён или внутри составного имени, которое это название покрывает. Так «г. Москва, Москва-Сити, …» и «Ханты-Мансийский АО, г. Ханты-Мансийск, …» подтверждаются (слово стоит отдельно или в покрытом составном имени), а ярославский «Ростов» не подтверждается словом «ростов» из «Ростов-на-Дону», даже если «Ростов-на-Дону» в десятке кандидатов вообще нет.

   Дополнительно для уровней `area` и `province`: привязка засчитывается только если каждое составное имя входа, не состоящее целиком из слов улицы топ-кандидата, покрыто хотя бы одним названием топ-кандидата (населённый пункт, район, любой регион). Непокрытое составное имя при привязке по региону почти наверняка означает город, который кандидат не нашёл («Камчатский край, Петропавловск-Камчатский, …» при топе «Елизово»), и адрес уходит в сомнение. Составные названия улиц («ул. Римского-Корсакова») на это не влияют, если геокодер нашёл ту же улицу.
2. **Более длинное совпадение предпочитается.** Если среди кандидатов любого `kind` (не только домов) есть населённый пункт, чьё название целиком входит в строку и содержит больше значимых слов, чем название топ-кандидата, топ-кандидат привязкой `locality` не подтверждается. Если такой кандидат есть, он дом и название его улицы целиком названо во входе (все значимые слова улицы есть среди слов строки), `classify` делает его топом и помечает результат полем `reordered: true`. Иначе (не дом, у дома нет улицы или улица во входе не названа) кандидат только блокирует привязку топа по `locality`, без перестановки: кандидат ниже по списку — не выбор геокодера, одного совпадения города для него мало. Пример: «ул. Красная Поляна, 5» при топе «Москва, Краснополянская улица, 5» и втором доме «Красная Поляна, улица Защитников Кавказа, 5» → «Город не указан», `reordered: false`.

Цена: строка вроде «Москва-Сити, Пресненская наб., 12» получит «Город не подтверждён», а не «Подтверждён». Это осознанно: сомнение честнее ложной уверенности, и такой адрес уйдёт в ручную проверку.

Проверка: (а) кандидаты «Ростов» первым и «Ростов-на-Дону» вторым, строка «Ростов-на-Дону, Будённовский пр., 1» → «Подтверждён», `top` = Ростов-на-Дону, `reordered: true`; (б) только ярославский «Ростов» среди кандидатов, та же строка → «Город не подтверждён»; (в) все 26 полных адресов из фикстур по-прежнему «Подтверждён».

### 5.3. «кв.» как квартал

Маркер `кв` сейчас всегда означает квартиру и обрезает хвост. Правило: если где-либо правее «кв N» в строке (в том же сегменте или в любом следующем) есть маркер дома («д», «д.», «дом», «влд», «стр», «корп»), то «кв» это квартал: сегмент сохраняется, обрезка хвоста не включается. Если «кв N» стоит после дома или маркера дома правее нет, это квартира, как сейчас. Голый номер после «кв N» без маркера («Ангарск, кв. 84, 5») остаётся квартирой: такая запись неоднозначна, и терять «5» безопаснее, чем отправлять в геокодер квартиру как дом.

Проверка: «Ангарск, кв-л 84, д. 5» (уже проходит), «Ангарск, кв. 84, дом 5» и «Ангарск кв. 84 д. 5» без запятых уходят в геокодер целиком; «Москва, ул. Тверская, д. 13, кв. 84» по-прежнему теряет «кв. 84»; «Ангарск, кв. 84, 5» теряет «5».

### 5.4. check-clean распаковывает xlsx и docx

`scripts/check-clean.mjs` для расширений `.xlsx`, `.xlsm`, `.docx` открывает файл как zip (своей минимальной реализацией чтения локальных заголовков zip с поддержкой методов `stored` и `deflate` через `node:zlib`, без зависимостей) и прогоняет те же шаблоны по каждому текстовому вхождению (`xl/sharedStrings.xml`, `xl/worksheets/*.xml`, `word/document.xml` и прочие `.xml`). Тест: собранный в тесте xlsx с UUID в ячейке ловится, `examples/sample.xlsx` проходит.

### 5.5. Режим «не запоминать ключ» и «Забыть ключ»

В блоке ключа появляются чекбокс «Запоминать ключ в этом браузере» (включён по умолчанию, как сейчас) и кнопка «Забыть ключ». Поведение:
- Чекбокс включён: ключ в `localStorage`, как в 1.0.
- Чекбокс выключен: ключ только в памяти страницы (`App.apiKey`), `localStorage` очищается от ключа; само положение чекбокса запоминается в `localStorage` под отдельным ключом `addrstd.rememberKey`.
- «Забыть ключ»: очищает поле, `App.apiKey` и `localStorage`. Доступна, когда ключ задан.
- Экран лимита с полем нового ключа подчиняется тому же чекбоксу.

Подсказка под полем объясняет оба режима одной фразой.

### 5.6. gitleaks и push protection

- `.github/workflows/gitleaks.yml`: на `push` и `pull_request` запускается `gitleaks/gitleaks-action@v2` по всей истории. Дополнительно шаг `npm test` и `node scripts/check-clean.mjs`.
- `.gitleaks.toml` с правилом на UUID Яндекса в дополнение к встроенным.
- В настройках репозитория через `gh api` включаются secret scanning и push protection (для публичного репозитория бесплатно). Делается командой, фиксируется в README в разделе «Разработка».

## 6. Что остаётся исполнителю

- Точный список стоп-слов и регулярных выражений в `algorithm.md` берётся из кода, а не пишется заново.
- Порядок коммитов: сначала перенос ядра в файл без изменения поведения (тесты зелёные до и после), затем исправления по одному, затем документация, затем npm.
- Форма псевдокода в `algorithm.md`.
- Минимальная реализация чтения zip в check-clean: через центральный каталог (локальных заголовков недостаточно, когда размеры вынесены в data descriptor), с защитой от zip-бомбы (ограничение на распакованный размер вхождения, например 50 МБ).
- Поле `reordered` живёт только в результате `classify`; новой колонки в выгрузке не появляется.
- Что именно показывают скриншоты README после изменения блока ключа: обновить `empty.png`, остальные не трогать, если блок ключа на них не виден.
